# 嵌入页按人取数：授权归属方案

> 2026-09-19 定稿。本文件是 TeKnowra fork 自己的设计记录，上游没有。
> 状态：2026-09-20 代码完成、本机浏览器实测通过（4 个 CRM 账号）；未上线。

## 要解决的问题

把挂了「按人授权 MCP 工具」的智能体（如「经营问数」）以嵌入浮窗的方式放进业务系统（CRM、OA）
给多人使用时，实测出现两个越权问题：

1. **令牌不分人。** 平台用浏览器里一个随机访客编号记住访客，整个浏览器只有一个。经理在某台电脑
   授权过，之后销售员在同一浏览器登录 CRM 打开浮窗，用的还是经理的授权。
2. **令牌发错人。** CRM 的授权服务（`/oauth2/authorize`）认的是它自己的服务端会话，与 CRM 前端
   页面的令牌登录是两套互不相干的登录状态。浏览器里残留的旧会话会被直接沿用，加上 `weknora-mcp`
   客户端设了免确认，整个过程没有任何页面——实测：CRM 页面登录的是 sales01，浮窗却以 admin 的
   身份取到了全部数据，用户无从知道授权的是谁。

## 原则（用户定的）

- **沿用 WeKnora 现有的授权实现，不另起一套。** 同一浏览器里授权一次，之后的对话都沿用。
- **只有宿主页面上的人换了，才需要重新授权；换回来，原来的授权还在。**
- 宿主退出登录时**不**清除：换回原来的人，沿用他之前的授权和对话（2026-09-21 最终决定。中间一度改成
  「点退出就清」，CRM 退出按钮里加过一行 `forgetIdentity()`，后来撤掉）。
- **不要求宿主系统配合改动**：嵌入式组件的宿主只贴一段代码。可以要求的只有嵌入参数（如 `hostUser`），
  不能要求对方改后端、登录或退出流程——别人的系统不会为一个嵌进去的组件改这些。
- 平台后端、令牌存法、授权流程一律不动。

## 方案

### 一、访客编号跟人走（TeKnowra 前端）

`weknora-widget.js` 的 init 多收一个可选参数（当前宿主用户的标识），经 postMessage 交给嵌入页；
嵌入页（`frontend/src/api/embed/index.ts` 的 `getOrCreateEmbedVisitorId`）按这个标识分别保存访客编号。
没传的渠道用默认那一个，行为与现在完全一致。

实施时发现方案漏了一样：**当前对话的指针**（`weknora-embed-session:<渠道>`）同样按渠道只存一份，
不一起分的话换人后会直接看到上一个人的对话。两样用同一个后缀一起分（`hostUser.ts`）。

后端不改：令牌仍按上游的 `embed_visitor:<tenant>:<channel>:<visitorId>` 存取。

### 一点五、平台生成的嵌入代码也要带上这个参数（2026-09-21 补）

「设置 → 网页嵌入 → 复制嵌入代码」替接入方生成三种代码。按人分开的能力原先只接在编程方式的
`WeKnora.init({ hostUser })` 上，生成的代码里没有、界面上也没提——照平台给的代码贴进去的宿主根本
用不上，而「宿主只贴一段代码」正是这件事的硬约束。三种形式各补一个入口：

| 形式 | 入口 |
|---|---|
| 浮窗、安全模式 | `<script … data-host-user="CURRENT_USER_ID">`，浮窗脚本的自动初始化读它 |
| iframe | 地址末尾 `#token=…&host_user=CURRENT_USER_ID`（与 token 一样放在 # 后面，不发给服务器），嵌入页启动时读它 |
| 单页应用 | 换人时页面不刷新、写死的属性跟不上，用编程方式 `WeKnora.init({ …, hostUser })`，用户变化后重新调用 |

占位符 `CURRENT_USER_ID` 原样留着等同于没填（否则所有人会落到同一个假用户名下）。代码框下面有一段
说明（`components/teknowra/EmbedHostUserHint.vue`）。要用不会变的 ID，不要用姓名、邮箱。

### 二、宿主传入当前用户（CRM 前端）

`crm-ui/src/utils/teknowraWidget.ts` 加载小部件时带上当前登录人。为此从「script 标签 data-* 自动初始化」
改成脚本加载后调 `WeKnora.init`，并盯着用户 ID：换人就重建浮窗（旧 iframe 里留着上一个人的对话）。
刷新页面时令牌先在、用户信息晚到，这段时间先不建，免得建两次白耗渠道的每分钟限流。传**用户 ID**（不变）而不是用户名；
19 位雪花 ID 全程按字符串传。

### 三、授权时必须现场登录（CRM 授权服务）

第一版做的是「确认页亮出当前账号 + 换个账号入口 + 关掉免确认」，本机测通后被用户否掉：
**那是把选择权交给了人**——sales01 看到确认页上写着 admin，不点「换个账号」直接确认，照样拿到 admin 的权限。

改成由不得人：走授权页（`/oauth2/authorize`）给第三方应用授权时，一律不沿用浏览器里
已有的授权服务会话，必须在弹窗里现场输一次账号密码；输的是谁，令牌就是谁的。能授权成谁，只取决于
知道谁的密码。

- 实现：`crm-auth/.../support/filter/FreshLoginFilter.java`（排在 `SecurityContextHolderFilter` 之前）。
  表单登录成功时在会话里盖时间戳（`TenantSavedRequestAwareAuthenticationSuccessHandler`）；
  授权请求（只拦 GET）进来时时间戳不存在或超过 60 秒就整个会话作废，流程自然走到登录表单；
  登录后回放授权请求，放行并用掉时间戳——一次登录只换一次授权。`FreshLoginFilterTest` 7 条。
- 免确认（`autoapprove`）保持打开：人刚输完密码，再问「确定是这个账号吗」多余。确认页不改。
- 顺带：前端退出登录（`DELETE /token/logout`）时把授权服务的会话一并作废。这只是「退出该退干净」，
  防线是上面那条。
- 这部分对所有授权场景生效（正常对话、设置页、跨空间共享），不限于嵌入页。
- 对定时任务无影响：它用创建人授权时存下的令牌，后台自动续期，从不走登录。令牌有效期（通行 12 小时、
  续期 30 天、不滑动）是建客户端时的默认值，本次不改（用户决定）；到期后创建人需重新授权。
- **默认对所有客户端生效，上线不需要任何配置。** 曾做成「按客户端开开关」，但「终端管理」的表单里没有
  扩展信息的输入框，开关只能改库——靠人去开的保护等于没有，遂改为默认开。只影响授权页；用账号密码
  直接换令牌的客户端（pig、app、小程序）不经过这里。个别客户端确要沿用已有登录时，在库里它的
  `additional_information` 加 `"force_login":"0"`，并删 Redis 键 `1:crm_oauth:client:details::<client_id>`
  （这条缓存永不过期、存在 Redis 里，重启 CRM 清不掉）。

### 三点五、MCP 服务自带的确认页（tyer-mcp-server）

授权时先弹的「Application Access Request / Allow Access」是 FastMCP 的 OAuthProxy 自带的，防的是
「混淆代理」：本服务允许任何程序自助登记、回跳地址自报。它的办法是把回跳地址亮给用户核对——
用户原话：「普通用户怎么能确认一串回跳地址？就是在无脑点绿色按钮」。和第一版 CRM 确认页同一个毛病。

改成由系统把关：环境变量 `MCP_ALLOWED_CLIENT_REDIRECT_URIS` 配回跳地址白名单（只认完整地址、
非本机必须 https、写错拒绝启动），名单之外的程序登记不了、也收不到凭据；**配了白名单才关确认页**，
两者在代码里绑在一起。没配则确认页照旧弹（已汉化，`tyer_mcp_core/consent_zh.py`）。
上线要在服务器 MCP 的环境变量里填 `https://<TeKnowra 域名>/api/v1/mcp-oauth/callback`。
注意 TeKnowra 对每个 MCP 服务只登记一次并记下当时的回跳地址，所以 TeKnowra 只能有一个对外入口地址。

### 四、顺带

授权完成后弹窗的落脚页是不带 token 的嵌入页地址，显示「缺少嵌入渠道或 Token」，像报错。
改成「授权成功，可以关闭此窗口」。

## 安全边界

保证：**正常使用下不同的人不会串用授权**；给第三方授权必须现场输密码（能授权成谁只取决于知道谁的密码）。

不保证：访客编号是上游的设计——存在浏览器里的一长串随机数，服务端不另行验证，知道它就能用；
`hostUser` 由宿主页面自报。用同一台电脑、同一个系统账号、同一个浏览器，且会用开发者工具的人，
能翻出前一个人的编号，以他的权限向这个智能体提问（只读；令牌本身在服务器上，带不走；授权最长 30 天）。
这与「在公用电脑上登录了网站没退出」是同一类风险，是用户知情后的取舍。

小部件保留了 `WeKnora.forgetIdentity()`（让嵌入页删掉当前宿主用户的访客编号和对话指针），
供确实想在退出时清除的宿主自行调用；CRM 不调用它。

曾考虑并否决的做法：由宿主**后端**签名担保当前用户、TeKnowra 据此分区存令牌（把上游 API 集成线的
签名令牌机制接到嵌入线）。否决理由：要宿主系统改后端——自己的 CRM 改得动，别人的系统不会配合。

## 实施顺序

三 → 一 → 二 → 四。三改动最小、对所有场景都有益，先做。
