# 聊天合同附件复用核查与Langflow最小接入方案

日期：2026-10-16。范围：只读源码核查、与封存M对应源归档比对、设计最小增量；不改产品代码、不变更M/N包、不上传真实合同、不运行产品写入接口、不上线。

业务要求：用户在TeKnowra对话框上传待审合同，合同作为该会话材料；企业制度/规则/模板预先放授权知识库。合同不自动创建知识库文档或进入共享检索。

## 追加核查：原合同审查智能体的聊天历史自动索引

2026-10-16按用户要求只读核对本机开发数据库中原始「合同审查」（854499ab-7e55-4be0-a681-807a096fea4e），不是V2/Eino/Langflow验收版本。原配置使用tyer-contract-review技能，原技能明确支持对话上传合同/粘贴正文及CRM传正文；审查清单通过CRM工具读取。原智能体未显式选择知识库；kb_selection_mode=all本身不能作为“绝无入库”的证据。

历史6条附件记录涵盖DOC/DOCX，已持久化解析正文，未找到同文件名或同标题的知识文档。现有名为「合同审查V2合成验收」的那份知识文档是后续合成验收资料，不等于原Agent上传合同自动入库。

**但原空间开启了聊天历史索引。** 当前原Agent关联50条聊天知识记录，其中47条未删除；以一个历史上传合同的40字连续原文样本做只读匹配，在该Agent关联的未删除__chat_history__知识记录中命中12条。没有导出合同全文或实际原文片段。结论是原文件没有被作为同名业务知识文档上传，但问答/报告及其中合同原文片段已通过自动聊天历史索引间接进入隐藏知识库；隐藏不等于没有入库，也不据此推断已对其他用户公开。

路径：internal/handler/session/qa.go:1944 completeAssistantMessage在回答完成后调用IndexMessageToKB；internal/application/service/message.go:374将原用户query与最终answer组合成passage并创建知识记录。它不直接把attachments字段全文作为独立文件入库，但贴入query的合同或报告引用均可能进入索引。

**因此下方最小接入方案必须增加一项：对本场景的合同会话禁用自动问答知识索引。** 不能仅阻止附件入库；后续追问、报告引用也须沿用该会话策略。不得擅自关闭整个空间的历史检索、删除旧索引或改动原Agent。实施后检查knowledge/chunk/索引无新增，消息和执行记录的保留与知识入库是两套策略。本轮未关闭配置或删除数据。原“临时附件服务自身不建知识索引”的结论仍成立，但不代表整个问答完成链路没有后续入库副作用。

## 1. 结论

现有TeKnowra已具备会话附件上传、异步解析、状态等待、原文件存储、消息关联、预览和清理链路；无需重建上传器/解析器或借知识库保存合同。当前Langflow不能直接接收这些附件，服务层明确拒绝，历史投影也主动去掉附件正文。

最小实现可先复用宿主已解析的**完整文本**，作为受限会话上下文送入原Langflow Chat Input，不新增画布文件上传组件、不把原始文件或平台存储凭据交给Langflow。必须同时处理解析失败、长文不完整、追问和会话范围，不能只删一行拦截。

该最小版本应明确限制：仅接收在既定输入预算内可以完整提供正文的文本合同；超限或需要未解析图片的合同不能宣称完成全文审查。若首批真实合同需要长文覆盖，应在同一会话附件服务上增加分页读取能力；这是扩展项，不用另建知识库或重新选框架。

## 3. Langflow当前缺口

### 3.1 明确入口拦截

`internal/application/service/session_agent_qa.go:238`：Langflow绑定命中后，只要req.Attachments、ImageURLs、ImageDescription或QuotedContext非空就返回“Langflow本阶段仅支持文本与已入库授权知识”。后面原生`req.Attachments.BuildPrompt()`虽已存在，但无法跨过这处门禁。

`internal/agent/langflowruntime/engine.go:90` 接口本身可以接收字符串query；它另行拒绝图片。解析后的文字可以作为输入，不需要Langflow处理原始PDF或DOCX。

### 3.2 解析失败/等待超时会跳过材料

`qa.go:1610` 的通用附件路径选择readyIDs，未完成附件被跳过；resolve错误记录后也可能继续问题执行。通用问答允许部分可用，并不满足“合同缺失不能输出审查结论”。合同任务需在模型调用前严格检查所选材料全部ready且有可用正文，失败/等待超时应明确提示，不继续生成无合同的审查报告。

### 3.3 默认长文选择不等于全文审查

`temporary_document.go:661`：每条消息最多5个附件，合计近似12000-token选择预算，按文件平分；长文按问题词命中选择最多16个片段，并非自动逐条审查全文。`ContentMode=selected_chunks`和SelectedChunks/TotalChunks已提供完整性线索。短文路径及近似token数也不能代替实际模型输入预算校验。

直接复用这份selected_chunks并声称“整份合同已审完”不成立。最小版本只接受完整、未截断且满足总上下文预算的解析文本；部分解析、空内容、OCR覆盖不足、超限均需明确结果范围或拒绝完整审查。全量长合同需要分页/分段覆盖能力，不能通过悄悄放大上下文或截掉后半段替代。

### 3.4 追问不会重新读原合同

`internal/application/service/langflow_history.go:13` 只保留用户文本和规范最终答案，不加载Attachments.Content。`langflowruntime/history.go`又有20完整问答/64KiB历史上限。用户第二轮问“再看违约责任”，不能仅凭上一轮报告回答完整原文问题。

应继续保留纯文本历史规则；为每轮另外构建受授权的会话材料上下文，从当前会话已关联附件ID重新读取。不能把所有附件正文塞回普通历史，影响其他引擎/会话隔离或反复扩大上下文。

### 3.5 文件引用与知识引用分开

现有附件预览是会话受权路由，MessageAttachment.URL是内部句柄，不序列化给客户端。新增输入不得暴露原始存储URL/临时capability；报告用“合同文件名+片段/段落定位”和“制度知识库source_id”区分来源。没有解析器实际页码元数据时，不能伪造准确PDF页码。

### 3.6 生命周期语义需要准确

当前临时原文件默认24小时清理，不是关聊天立即删除；清理不等于同步抹除已写入消息的附件文字、旧回答、备份或LF执行trace。仓库GetScoped不直接过滤ExpiresAt，物理清理有时间间隔，新接入需显式判断可用性/过期，不能把有TTL字段理解为到期瞬间全面不可访问。

当前原生服务允许分叉会话读取已复制历史中引用的同tenant父附件。若本场景执行“本次会话材料”的严格范围，最小LF材料集合只选当前会话直接上传并已关联消息的文档，不新增任意ID/分叉继承访问，也不修改其他引擎的原有分叉语义。

Langflow仍会保存执行trace，不因ChatInput/Output关闭本地消息记忆就保证零落盘。业务要求本轮是“不自动进知识库”；若未来要求关闭即销毁/全文不留痕，应另定保留和清理策略，不能默认为已经满足。

## 4. 建议的最小改动方案

### A. 第一版可用接入：完整文本合同，不新增画布组件

运行链路：对话上传 → 宿主异步解析 → 附件就绪/完整性检查 → 当前会话材料上下文 → 现有Langflow Chat Input → 授权制度检索/CRM/技能 → 合同与制度分源报告。

1. **复用前端与解析器。** 沿用现有AttachmentUpload、临时附件API、消息attachment_ids、预览、解析队列及存储，不新增KB/知识文档，不走embedding入库链。
2. **新增明确的LF附件能力开关/发布策略。** 默认保持旧文本行为；开启后允许受控解析文本，继续拒绝未支持的直接图片/音频和其他输入。合同必需资料由所选附件/当前任务约束决定，普通问答不能被全局改成“必须有附件”。策略应纳入固定发布校验，不能由模型或任意客户端临时扩大。
3. **补齐严格结果传递。** 在现有解析等待后传递就绪/跳过/失败等结果给LF材料校验；缺资料、正文为空或部分选择时停止合同审查，保留清晰持久提示。只对启用附件策略的LF路径生效，不全局改变原生问答的容错语义。
4. **建立会话材料投影。** 使用当前请求中已验证ID，并支持从当前会话历史关联中选择同一份合同供追问；ID来自服务端会话范围，不能接受外来tenant/session或其他会话引用。默认只有一份时明确延用；多份合同或修订版时列出候选并让用户明确选择，不自行混合。每轮重新核查文档仍在、未过期、ready及完整正文可用，删除后不从旧消息正文复活。
5. **作为本轮文本输入接入。** 用带文件名、文档ID、解析版本/内容摘要、完整性和定位的受限上下文组装原Chat Input；不污染持久用户问题、不更改纯文本历史策略。不把临时存储路径当用户下载链接。复用现有不可信附件包装；合同内指令不作为系统/工具授权。
6. **保留制度/工具授权。** 附件归当前调用人的会话；共享Agent的制度可按源空间授权检索，不能把合同归属切到发布者。MCP继续本人OAuth，技能继续原生管理，图结构与组件改变后按现有固定发布流程发布新版本。

首版影响范围按职责预计为：`handler/session/qa.go`的LF专用严格解析结果接线；`service/session_agent_qa.go`附件门禁；新增独立会话材料投影helper；绑定/发布能力策略与验证；对应定向测试。无需数据库新表、重写文件解析器、知识库自动入库或新的合同专属执行器。具体字段与函数签名待实施计划确定，不在本核查中先改代码。

Agent文件类型、OCR与解析等待配置已有入口；第一轮尽量复用，仅在确需让用户选择会话内多份材料时增加小范围选择交互。共享Agent的调用者合同访问必须与源空间制度授权分开验证。

### B. 需要长合同全文覆盖时的最小扩展

在现有TemporaryDocument完整content/chunks基础上，增加**通用会话材料分页读取能力**，复用任务级能力桥，而不是把合同伪装成技能或上传到LF Files/知识库。

- 输入仅当前会话允许的document_id与受限offset/limit等，返回文件名、片段序号、正文、next_offset和完整性信息；拒绝任意路径/URL/跨会话ID。
- 每次读取检查当前人员、会话、文档状态/期限，返回限量文本；不读取宿主凭据。
- 若需研发在画布显式连接，增加一个通用“TeKnowra会话材料”工具组件，并扩展绑定kind/发布组件指纹/节点许可；这不是单改Prompt可完成的现有能力。
- 全文审查必须设计覆盖记录/逐段处理及汇总，不能只给Agent一个search工具就声称完整覆盖。关键词搜索仅用于定位/追问，不能代替逐段覆盖。
- 当前仅有Seq/Start/End/ContextHeader等通用片段信息，准确页码取决于解析器元数据。B阶段也不自动解决OCR漏页或复杂表格正确性。

建议先以首批真实合同体量判断A是否足够；如果真实样本普遍超过A的完整输入预算，直接做B，不交付一个默默只看片段的“全文审查”。

## 5. 实施后需做的针对性验收

1. 在聊天中实际上传可解析PDF和DOCX；按真实配置等待、预览和读原文；核对没有新增knowledge/KB索引记录。
2. 同会话不重复上传就能追问原文；新会话/其他账号/其他空间不能读取；共享Agent运行中附件仍属于调用人。
3. 解析慢、失败、超时、空内容/不完整OCR时，不输出“已审完整合同”；提示刷新后保留。
4. 短合同全文输入成功，长合同selected_chunks被明确限制；如果做B则核对完整分段覆盖和可追问定位。
5. 同会话多份/修订合同不会混用；删除/过期后新一轮不能从旧附件正文缓存复活原文。旧回答仍是历史内容，不承诺追溯删除。
6. 报告区分合同原文与制度引用；未知页码不编造，临时票据/内部存储URL不进图或前端返回。
7. 已有纯文本、多轮、知识授权、共享与CRM本人OAuth定向回归，M/N包保持不可变。新能力验证后另固化新版本，不原地改旧包。

本轮未跑这些新增能力实测；现有附件单测覆盖范围包括全文小文档选择、长文分片预算、OCR条件、分叉访问、元数据持久化等，源码中已存在的断言不等于本轮重新执行通过。
