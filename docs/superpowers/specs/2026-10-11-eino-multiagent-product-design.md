# Eino 多 Agent 原型产品接入设计

状态：用户回复“开干吧”批准实施，2026-10-11 本机实施及限定范围验收完成；生产未上线。本文下述“源码事实”保留实施前快照，实际结果见 D:/TeKnowra/research/selection/eino-delivery-cost-20261011/多Agent产品接入验收.md。

## 目标及范围

用户已选择把已有多 Agent 原型接入 TeKnowra 产品，以验证企业场景交付能否复用公共底座。新增 `business-review-multiagent-v1`，由一个主 Agent 根据问题自主选择合同专家、信用专家，支持单专家及双专家任务。通过平台 Agent 配置绑定模型、明确知识库和一个本人 OAuth CRM MCP 服务，在正式聊天展示专家执行步骤、知识引用和最终结果。

本轮只读、单次任务；旧合同审查、信用查询和知识摘要定义保持可用。实施地点为当前本机工作区，不上线生产、不改共用账号、不覆盖已有未提交修改、不提交密钥与本机配置。并行专家、动态创建专家、业务写入、长期记忆、技能、画布资源连接器及所有设计模式均不在本次范围。

## 源码事实

- 研究模板 `research/selection/eino-next-20261009/model/templates/delegation.go` 使用 ChatModelAgent 和 AgentTool，已经有真实模型选择专家的实验记录，但材料读取回调是合成材料，未接正式权限、引用与聊天持久化。
- 产品目录 `internal/agent/einodef/catalog.go` 当前只有三个定义；运行清单 `internal/agent/einoruntime/publication.go` 同样仅有三个构建器。
- `internal/application/service/agent_service_eino.go` 在需要 MCP 时直接进入只读工厂，不能同时装配知识能力；`eino_definition_config.go` 明确拒绝混合能力。
- `einoruntime.Engine.Execute` 已提供任务预算、知识输出前复核、引用和完成事件；`customer_credit.go` 已提供本人权限内的客户读取及输出前访问检查。
- 现有步骤有 run_id、node_key、definition_version；聊天事件和数据库已能承载步骤。多 Agent 尚无明确专家归属适配。
- 现有结构化模型节点拒绝 ToolCalls，模型调用上限为四次，不能直接作为 ADK 主、子 Agent 模型。

## 方案选择

采用平台内 ADK 执行适配，复用当前 Engine 的输出与完成链路。相比独立 Eino 服务，它不需要跨服务传递用户身份和重新实现权限、OAuth等待、聊天事件。相比复制一个专用场景执行入口，它能保持新增业务定义使用现有发布目录。

外层 Graph 仍可由 IDE 组织并生成，ADK 专家定义和平台工具桥接由研发写代码。不会宣称专家拓扑和平台资源已能完全在画布下拉配置。

## 能力装配与身份

把平台授权知识读取与只读 MCP 调用提取为可组合能力；同一个发布定义可声明两者，但声明不等于权限。配置必须为明确知识库、恰好一个本人 OAuth MCP 服务，工具名单只含知识检索和三项既有 CRM 只读工具。仍拒绝技能、沙箱、浏览器、网页检索、记忆和共享 Agent 越权执行。

主 Agent 只获得两个已发布专家工具，不获得通用 MCP 或任意知识库选择权。合同专家只获得授权知识能力，信用专家只获得三项固定 CRM 只读能力。服务、用户、租户和资源范围由平台捕获并校验，不由模型参数指定。继续使用现有工具目录、参数校验和固定参数机制；雪花 ID 保持字符串。

合同专家使用原任务中明确的合同信息，信用专家使用原任务中明确的客户名称。主 Agent 改写专家请求不能扩大原任务授权范围或替换客户身份。专家调用次数受限，不能重复调用专家以无限重试。

## ADK、模型与任务预算

产品化 ToolCallingChatModel 适配，使用平台已有 chat.Chat 与 ReadModel。支持 ADK 本次需要的文本、工具定义、工具调用回传、工具结果、供应商推理元数据和 usage；不支持的多模态及模型选项显式报错。未完整结束、截断、未知工具或非法参数不作为成功答案。

主、子 Agent 在同一个任务 context 和 run_id 中运行，专家先顺序执行，避免当前 RoundSteps 可变切片的并发写入。所有模型请求共享累计次数与 token 记录；本定义模型调用上限为 16，主 Agent 最大 5 次迭代、专家最大 3 次迭代，每位专家的业务执行至多一次。保留当前累计活动 120 秒、授权等待 600 秒、总墙钟 720 秒和一次重新授权预算。旧定义仍保留原调用上限。

CRM 业务读取复用现有本地确定性处理；实际信用字段不作为主 Agent 自由推断的材料。平台最终呈现已验证的专家结果，避免主 Agent 重新生成金额、额度或未经验证的授信结论。合同知识仍按现有配置使用模型生成与事实复核。

## 专家结果、引用与最终复核

专家输出是独立结果对象，包含专家标识、完成状态、审核后的文本及知识引用。主 Agent 决定调用对象，平台按已成功执行专家结果组合最终答复；不能由模型伪造“专家已经完成”。无实际专家执行、任何必需专家失败或结果缺失，任务不发成功完成事件。

知识引用使用真实平台 SearchResult，合并时按来源标识去重，最终沿用当前授权过滤与资料内容复核。信用结果在最终发布前再次检查客户访问权，不能仅检查专家结束时的权限。权限变化或任务取消时停止输出业务结果。

本轮验收不做贷款、授信或订单批准决定；仅呈现合同制度和本人有权读取的信用档案，明确未下单、付款或回写。

## 事件、等待与恢复

现有步骤事件增加明确专家归属：主 Agent 决策、合同专家检索/分析/复核、信用专家客户查找/访问检查/读取、任务汇总。所有步骤使用同一任务 run_id，并采用专家前缀 node_key，保留稳定迭代序号。步骤、工具调用、引用与完成状态可在刷新后读回；事件编号不能因重复专家阶段发生覆盖。

OAuth 卡片沿用平台现有调用桥接。等待发生在当前专家步骤中，授权后恢复同一任务和参数，不新建任务、不借用 admin 授权、不重置全局预算。这是在线进程内暂停/续跑；进程重启后的断点恢复不在本次承诺内。

前端先复用已有步骤展示，保证用户能辨识专家及其调用。只有现有组件不能呈现上述信息时才做必要的小范围适配，不新增企业用户编排画布。

## 实施与验收要求

先添加失败用例，再实现能力组合、ADK 模型适配及专家执行。自动测试覆盖单专家/双专家路径、真实调用与结果一致、专家隔离、统一预算、引用合并、任务取消及错误不完成。不能用提示词替代权限测试。

本机正式产品验收：

1. 新建独立多 Agent 验收 Agent，绑定合成合同知识库、现有 DeepSeek 和本人 OAuth CRM 服务；不修改三个既有 Agent 的绑定。
2. 合同问题只运行合同专家，信用问题只运行信用专家，综合问题运行两位专家；核对步骤、CRM 只读工具、答案和引用。
3. 对需要用户登录的 CRM 调用，验证授权卡、等待和同一任务续跑；需要用户自行登录时清楚交接，不输入密码。
4. 刷新页面并查询持久化元数据，确认同一 run_id、专家步骤、引用和完成状态。
5. 对原三个定义做必要回归，保存截图及不含凭据的结果报告。未通过的项目明确列出，不以 API 或研究测试替代正式聊天验收。

具体业务代码与公共适配的工时分别记录，但没有人工交付基线前不计算成本下降百分比。本机发布成功也不意味着生产上线或所有 Agent 模式验收完成。

## 风险与回退

新增模型适配与能力组合属于本次主要风险，测试应先覆盖供应商元数据、事件归属和权限。模型专家选择质量需真实样本检查；有限样本成功不保证长期准确。

发布仍以服务端不可变定义清单及本机 Agent 绑定控制。失败时移除新增 Agent 的本机绑定并恢复已保留的本机后端版本；不删除会话、数据库或 OAuth 卷，不变更旧定义或生产容器。

## 设计自审

范围覆盖用户已选择的主 Agent＋两类专家、资源身份、聊天记录、授权等待和复用目标。明确采用顺序委派而非并行；明确平台组合专家结果而非未经复核的自由业务结论；明确在线等待与重启恢复的区别。尚未实施，需审阅后编写文件级实施计划并执行。
