# TeKnowra Eino 企业 Agent 首期范围与执行契约

日期：2026-10-10。状态：待评审设计，未实施。读者：产品负责人、平台研发及业务 Agent 研发。

首期目标是让研发交付第二个 Agent 时，能够复用 TeKnowra 的身份、知识授权、按人工具授权、停止与执行记录，把主要开发工作放在业务流程上。采用 Eino 进程内运行；企业用户选择已发布的 Agent 并按权限使用，研发负责 IDE 编排、代码审查和发布。首期不建设面向企业用户的流程画布。

本设计不要求先全面重构平台。已有 AgentEngine、Caller、Principal、工具注册和事件处理继续使用；只补齐 Eino 场景实际需要的执行契约。现有合同审查及其他 Agent 的既有路径保留。

## 2 首期业务范围

首个交付是合同审查 V2 的只读正式版本：读取授权合同与政策，识别事实、政策版本、风险和缺失信息，给出来源引用。不提交审批、不付款、不回写 CRM。

只读 MCP 的第一批业务工具限定 CRM-MCP 的 `find_customer` 与 `get_customer_credit_control`。合同确实关联客户且用户要求核对客户信用时才启用该分支；采购合同没有对应客户或缺少业务绑定时，仍只做知识审查，不能把不相关 CRM 结果拼入意见。多匹配、无匹配或无权访问时返回待确认/不可用，不自行选人或推断客户信用。

客户绑定由用户在有权访问的业务选择流程中确认，后端再次验证，Agent 不得把模型生成的任意客户 ID 当作已授权绑定。CRM 雪花 ID 始终为字符串。授权目录/自检只用于接入验收和用户明确要求的能力查看，不作为每次业务取数的强制步骤。

第二个样板是简单的“客户信用只读查询”：复用上述两工具和同一执行契约，只改变业务输入、提示词、查询顺序和展示。它用于检验公共能力是否真实复用，不扩展成另一个全功能产品。

| 首期包含 | 首期不包含 |
|---|---|
| 本工作区 Agent 发布和有权用户使用 | 跨租户共享 Agent 发布与执行 |
| 授权知识检索及引用，按人 OAuth 只读 MCP | 写工具、审查回写、付款、发信 |
| 固定工作流，明确条件分支 | 通用自主规划、multiagent 运行平台 |
| 授权卡片、等待、同任务恢复和停止 | 服务重启后续跑、后台长任务、长期记忆 |
| IDE 编排生成代码、人工审查、服务端发布与回滚 | 动态执行浏览器提交的图代码、企业用户画布 |

不支持项必须显式反馈，不能静默换成普通 ReAct 路径或其他服务账号完成。

## 3 职责和数据流

TeKnowra 负责身份解析、Agent 访问检查、知识范围计算、工具政策、OAuth 凭据、模型配置和运行记录。Eino 负责业务节点顺序、条件分支、受控模型调用、结果组织和节点状态。CRM 等业务系统继续判定其自身的数据权限。

执行顺序：平台确认用户与 Agent 权限 → 构建运行输入 → Eino 检索授权资料 → 按业务需要请求只读工具 → 必要时等待 OAuth → 重查权限并继续同一调用 → 分析与验证 → 输出前校验 → 通过现有事件链路发送并保存。

知识、MCP 和直接 HTTP 业务接口分别承担自己的授权规则。“通过平台登录”不代表已获得 CRM OAuth，也不代表对任意 HTTP 地址有访问权。首期业务数据只能通过已注册的只读 MCP 适配器获取，不增加通用 HTTP 节点。

## 4 统一执行契约

这是后端内部契约，不是新建远程 API。下列字段表达语义，落地时优先复用既有类型，不要求建立一套平行 DTO。

| 信息 | 可信来源与规则 |
|---|---|
| Caller：用户、租户、角色 | 平台认证结果；模型和浏览器不能覆盖 |
| Principal：主体类型和 ID | 平台身份绑定；首期限定已登录 web_user，不为 API/IM/嵌入入口猜测用户 OAuth |
| Agent ID、定义 ID 与定义版本 | 后端加载已发布定义；执行开始后固定，发布新版本不改变正在执行的运行 |
| session/message/run/node/tool-call ID | 平台/执行器生成并贯穿事件与持久化；授权恢复保留同一 run 与 tool-call ID |
| 初始知识范围 | 平台按 Agent 配置与用户权限计算；后续只允许缩小，不因运行中新增权限而自动扩张 |
| 资源来源租户 | 从资源元数据解析；执行租户切换不改变 Caller |
| MCP 服务及工具上界 | Agent 发布定义 ∩ 平台工具政策 ∩ 请求收窄范围；OAuth 只提供身份，不扩大工具集合 |
| 输入及客户绑定 | 用户输入可进入提示词，身份/权限/绑定须服务端校验；不得由提示注入改变 |
| 模型及预算 | 复用平台模型配置；凭据不进入图配置、提示词、事件或执行记录 |

### 节点只使用三类公共能力

1. 知识读取：调用现有检索服务，返回带知识库、文档、分块及来源租户的证据；复核规范内容与启用状态，摘要和正文标识区分。
2. 只读工具调用：通过既有工具注册、MCPTool、MCPManager 和授权 Gate 调用，不由图直接访问 token、网络客户端或共享凭据。
3. 执行反馈：通过现有 EventBus 输出节点、工具、OAuth 和终态事件，交给现有聊天处理器与持久化服务；不另造聊天协议。

定义提供业务节点和允许的工具/知识需求，平台提供上述能力。第二个 Agent 不复制 OAuth 等待和权限校验实现。

### 知识与工具结果的有效性

检索前、证据进入模型前、授权恢复后及最终输出前重新校验相关权限。撤权、来源停用、内容变化或用户身份变化时终止本轮并清除待输出答案，不发布引用或成功事件。模型已收到的内容和先前合法显示的内容无法撤回，首期承诺是阻止后续读取和未发送输出。

MCP 工具结果不冒充知识分块引用。记录服务、工具、调用主体、取得时间、业务对象和结果摘要；若 CRM 没有可用的“当前记录访问权限”检查入口，不能声称能够在取数后立即捕捉所有下游撤权。该业务结果发布能力须先补充下游校验契约并验收；否则对这条分支返回能力未就绪，不能跳过检查继续总结数据。不得用每次重新完整执行工具替代记录级权限检查。

## 5 授权等待与任务生命周期

逻辑状态：`running → waiting_auth → running → completed`；任意非终态可进入 `canceled`、`failed` 或 `timed_out`。这些是验收语义，先映射既有事件/消息状态，不强制新增任务数据库表。

- 使用一个保留停止信号的运行根 context。活动执行总预算拟为 120 秒，授权等待总预算拟为 600 秒，整体墙钟上限拟为 720 秒；预算初值沿用已验证试点习惯，支持发布配置，不承诺固定性能。
- 活动预算是累计模型、检索、工具及验证时间；人工等待消耗等待预算，不消耗活动预算。不能在每次恢复时重新发放完整运行预算。首期一个运行最多发起一次重新授权等待，避免无限循环。
- 单次模型最多 45 秒；MCP 调用按平台允许的服务级限额与剩余活动预算取最小值，发布校验拒绝超出总预算的配置。单独调大服务超时不能延长运行根预算。
- 授权成功只完成授权步骤。使用相同运行身份、参数和工具 ID 重查政策，重新创建实际调用 context；旧 CallTool context 不能用于恢复。继续通过相同工具入口，停止信号必须仍可传递。
- 停止、拒绝、等待超时及总预算耗尽进入终态，迟到 OAuth callback 可以更新用户授权，但不得恢复该终态运行；用户须发起新任务。
- 同一 pending decision 仅允许一次成功恢复。只读传输重试有界；不把 Gate 去重称为业务写操作幂等，也不在首期执行写操作。
- 活跃运行按进程内任务处理。刷新后可回放记录；是否还能显示与操作活跃授权卡片按现有 Gate/SSE 重新订阅能力验收。服务重启或等待失去运行主体时明确失败并提示重新发起，不宣称持久化续跑。

## 6 结果、异常与记录

正常输出包含审查事实、政策依据、风险、待确认事项和建议。模型生成的结论必须与证据区分，不能把工具调用失败、权限拒绝或空结果改写成“业务不存在”。工具失败是否允许仅知识审查由定义声明，默认关键依赖失败则终止；可选分支跳过时答案必须说明该项未核验。

| 结果类型 | 对用户的行为 | 后端约束 |
|---|---|---|
| auth_required | 同任务显示授权卡片 | 未授权前不调用业务 handler |
| forbidden | 明确权限不足 | 不发 OAuth 卡片，不改账号重试 |
| canceled / timed_out | 明确停止或超时 | 终态后不继续工具或输出成功 |
| auth_revoked / source_changed | 提示需重新发起 | 丢弃待输出草稿，不能输出旧证据 |
| transport_error | 说明工具暂不可用 | 只读有限重试，保留失败记录 |
| invalid_evidence / invalid_answer | 说明审查未完成 | 不以有文字/HTTP 200 作为业务成功 |

记录至少包含定义版本、身份标识（无令牌）、节点顺序与耗时、授权等待结果、工具调用 ID、脱敏参数、来源 ID、终态和失败原因。默认不记录原始业务工具响应或敏感正文作为运行日志；会话内容仍按平台访问控制管理。凭据只由现有 OAuth 存储和适配器读取，不能被复制到设计、执行轨迹或模型输入。

模型调用费用与工具耗时必须能归属到运行；授权等待单独统计，避免把人等待显示成模型耗时。首期提供现有会话内执行过程和历史回放，不承诺独立运维控制台或全套监控平台。

## 7 研发编排和发布契约

研发在 IDE 中设计图、生成代码，业务节点只依赖公共能力。生成图作为普通 Go 源码纳入审查和测试，不允许节点读取用户 token 或绕过工具适配器；生成代码本身不是权限边界。

已发布定义包括稳定定义 ID、版本、输入要求、知识绑定策略、工具名单、支持能力、预算和失败策略。第一步可使用后端代码注册和部署配置，不先建定义数据库或发布后台。Agent 到定义映射由管理员发布，不允许用户通过聊天请求切换引擎。

回滚通过恢复前一代码版本和服务端映射完成；进行中的运行保留其已固定版本，进程重启则按首期失败语义处理。旧合同审查配置与既有非 Eino 工厂路径不改写。部署与公网验收须另遵循接管手册，设计评审不授权提交、发布或生产操作。

## 9 实施拆分与评审重点

实施次序是：先修复并验收共享 MCP 授权等待边界，再交付仅包含运行身份/预算/能力入口的公共组件，随后接入只读 Eino 工具节点并发布两个样板，最后完成正式聊天端到端及兼容验收。每步独立可回滚，不先重写整个 AgentQA，也不先搭建独立 Agent 服务。

后续详细实施计划应逐项对应 A1–A12，注明必要产品文件、测试与回滚方法；本稿是设计规格，不含已授权的产品修改任务。当前用户要求先保留产品状态，因此本轮只保存设计。

评审重点：首期是否限定本工作区/只读/进程内运行；合同中的客户信用查询是否有明确业务需求和可信绑定；CRM是否能提供读取结果的输出前访问校验；120/600/720秒预算与单次重新授权限制是否符合预期；是否接受第二个轻量样板作为公共能力复用的交付门槛。

只有 A1–A12 在明确范围内验收通过，才称首期“可复用企业 Agent 执行链路”完成。自主规划、multiagent、写操作、持久任务和跨租户共享需要各自的能力定义与验收，不以本期完成替代。
